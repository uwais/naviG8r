# Android FCM shipment notifications — technical design

**Status:** Design accepted by Luna-High (Senior Software Engineer) and Astra-High (Staff Software Engineer) on 2026-10-11; implementation and development Firebase validation are complete on the feature branch. Production rollout remains gated on production Firebase operations and explicit persistence-mode approval.

**Branch base:** `origin/main` at `b7572f4` (PR #142 merged).

## Goal and scope

Deliver privacy-safe Android system notifications for shipment updates and new conversation messages, including when NaviG8r is backgrounded or closed. The existing authenticated in-app notification inbox and shipment conversation remain the source of truth. A push is a prompt to open the app and refresh that data; it is not a second message store.

This phase targets Android with Firebase Cloud Messaging (FCM). It does not add iOS/APNs, WhatsApp, SMS, arbitrary local reminders, notification actions that change shipment state, or a separate notification microservice. System notification text and in-app event copy remain English; user-authored message content is not translated.

## Existing system

- `apps/driver_pilot` is the Flutter client; Android application ID is `com.navig8r.pilot`.
- Phase 1 provides authenticated grouped inbox and shipment conversation APIs, recipient-specific `Notification` rows, per-shipment grouping, and tap-through to `ShipmentConversationScreen`.
- Current shipment notifications are generated with workflow/message state and persisted through the API's existing Store persistence path. The API supports PostgreSQL and a single-process FILE adapter.
- No Firebase SDK, FCM sender, Android notification channel, device-token registration endpoint, or push delivery worker exists yet.
- API entry binds to `0.0.0.0`; mobile builds can receive an API URL via a Dart define, enabling local-network device testing.

## Product and delivery decisions

1. **Reuse current events and recipients.** Push only after an existing authorized in-app `Notification` row is committed. Cover the current catalog: carrier acceptance/booking, trip start/completion, POD submission/acceptance, payment status, and new conversation messages. Respect the existing active shipper/carrier recipient fanout. Do not send to OPS, FINANCE, or ADMIN by default.
2. **One visible Android item per shipment.** Use one opaque stable presentation key per recipient/shipment as Android's notification tag, with integer ID `0`, so subsequent events replace that item's title/body/time. Include this opaque presentation key separately from the notification ID; it is only for display replacement and cannot authorize a route. Do not add a custom Android group-summary notification; leave any grouping to Android. FCM may coalesce undelivered messages across shipments, and the app always reloads the canonical inbox on open.
3. **Generic lock-screen copy.** Use a generic title/body such as “Shipment update” / “There is an update for a shipment.” Do not include message bodies, OTPs, phone numbers, personal names, addresses, exact payment amounts, or other private shipment data in FCM payloads or notification previews. Do not include a bearer token or treat any payload identifier as authorization.
4. **Tap-through uses current authenticated authorization.** The payload carries an opaque canonical notification ID, opaque presentation key, and schema version. On an initial unauthenticated launch, retain the opaque notification ID for a bounded period through sign-in. The authenticated open resolver derives recipient organization/shipment from the canonical row and bearer user identity without requiring a preselected organization; it verifies the user remains an eligible recipient with active membership and shipment/conversation access, then returns the permitted route or safe not-found/access result. Never trust payload IDs to select an organization or authorize access. Cancel pending routes on explicit logout, account switch, expiry, denial, or stale asynchronous auth-generation result; preserve only across the expected signed-out-to-signed-in transition. Taps refresh canonical inbox/timeline data; they never mark a notification read solely because it was tapped.
5. **Foreground/background presentation.** FCM notification payloads are displayed by Android while the app is backgrounded/terminated (subject to Android delivery, app state, and force-stop behavior). In the foreground, handle `FirebaseMessaging.onMessage` and show/update a local Android notification. Set FCM Android notification `tag` to the opaque presentation key and integer ID to `0`; foreground local display uses that same pair and channel. Derive the key from the FCM data payload, not from Android notification metadata. Verify the pinned Flutter plugin calls Android `notify(tag, 0)`; if it cannot, select a compatible plugin/version before implementation. Do not add a custom group-summary notification. Handle FCM background taps (`onMessageOpenedApp`) and cold-start taps (`getInitialMessage`), plus local-notification response and terminated-launch callbacks, through distinct callback paths.
6. **Permission timing.** Create a stable, user-visible Android channel for shipment updates. On Android 13+, request `POST_NOTIFICATIONS` after explaining the value, such as when a signed-in shipper/carrier opens Notifications or opts in. Register a device only after the user grants permission and opts in. Android permission/channel state is client/OS state: the server cannot verify it and may receive a stale client-reported hint. If permission is denied or later disabled in settings, the in-app inbox remains usable; the OS suppresses tray presentation. Do not repeatedly prompt after denial.
7. **Device ownership.** A registration belongs to an authenticated NaviG8r user and one stable app installation, not to a shipment or caller-supplied user ID. Keep installation identity stable across FCM token rotation. On account reassignment, revoke the prior registration and increment an ownership generation; on logout, attempt authenticated server revocation before clearing local auth, then clear local pending routes and account-scoped state. Retry revocation/reconciliation on next authenticated launch if offline. Invalid-token cleanup must compare token and generation so a stale provider result cannot revoke a newer token. Already accepted/in-flight pushes cannot be recalled; never promise immediate suppression after offline logout.
8. **Reliable delivery.** Persist a `PushIntent` atomically with the canonical in-app notification and source transition. At intent creation, snapshot the currently active, consented installations for each eligible recipient; do not replay old intents to installations registered later. Create one `PushDelivery` per `(notificationId, deviceId, ownershipGeneration)`, each with independent status/attempt/lease fields. Claim and persist a lease through the common mutation coordinator, send outside the coordinator, then conditionally record provider outcome only if the lease and device ownership generation still match. Retry transient errors with bounded backoff/jitter, honoring provider retry guidance within configured limits. Delivery failure never rolls back a committed shipment event or conversation message. Provider acceptance means accepted for delivery, not displayed or read. Duplicate sends may re-alert or resurrect a dismissed tray item; canonical inbox state remains authoritative.
9. **One persistence owner for first release.** Keep push device, intent, and delivery state inside the existing Store snapshot and persist only through a common mutation coordinator shared by HTTP requests, background timers, and the push worker. A worker claim is persisted before network send; network I/O occurs outside the coordinator; completion is conditionally persisted under it. This prevents a later full-Store save from erasing worker changes. In FILE mode, production sending is disabled by default and can be enabled only for an explicitly approved single-process pilot with `PUSH_ALLOW_FILE_PRODUCTION=1`; FILE has no multi-instance lease safety. PostgreSQL remains required before horizontal scaling or broader rollout. Do not write push rows through an independent repository while other code rewrites the full Store snapshot.
10. **Operational boundaries.** Configure separate Firebase projects/credentials for development and production. Keep server-only FCM service-account credentials in deployment secrets; never bundle server credentials in Flutter or commit them. Firebase's public Android app configuration is client configuration, not a substitute for server credentials. The sender may use Firebase Admin SDK or the FCM HTTP v1 API; no Firebase Analytics, Cloud Functions, or new Firebase database is required for this feature.

## Architecture

```text
Shipment/message transaction
        │
        ├── existing Notification row (canonical in-app alert)
        └── PushIntent (one per canonical notification)
                    └── PushDelivery (one per eligible installation snapshot)
                    │
                    ▼
             FCM delivery worker ─────► FCM ─────► Android system tray
                                                   │ opaque notification ID
                                                   ▼
                                      authenticated open resolver
                                                   │
                                                   ▼
                                authenticated grouped inbox/timeline API
```

The worker sends one safe push per snapshotted eligible installation for a notification intent. The payload contains a schema version, opaque notification ID, opaque presentation key, and generic title/body. It contains no message body or rendered sensitive fields. The authenticated open resolver verifies the notification belongs to the current user and that current membership and shipment access still allow the route. Before sending, the worker rechecks recipient eligibility and device ownership generation; it cannot verify Android OS permission/channel state. Client-reported permission is only a hint, and Android itself controls display. Provider acceptance is not proof of device display or user read.

## Data and API changes

Add a minimal `PushDevice` record with stable internal ID, authenticated `userId`, platform (`ANDROID`), stable app-installation ID, FCM registration token, environment, client-reported notification permission/consent hint, `ownershipGeneration`, and created/updated/last-seen/revoked timestamps. Enforce token uniqueness and bounded active installations per user. Do not store selected shipment/org data on the device record. The token must be encrypted at rest if supported by the existing DB deployment; otherwise restrict access and exclude it from API responses, exports, and logs. Registration accepts the token and installation metadata only; identity is derived from the bearer principal.

Add a `PushIntent` record with ID, unique canonical notification ID, recipient user/org IDs, shipment ID, and creation/expiry timestamps. Add a `PushDelivery` record per eligible device snapshot with intent ID, device ID, snapshotted ownership generation, status, attempt count, next-attempt/lease owner/lease expiry/provider-accepted timestamps, and bounded provider error code. Enforce uniqueness on `(notificationId, deviceId, ownershipGeneration)`. Record outcomes independently per installation. Store no notification text or message body in either record. Keep successful delivery metadata only as long as needed for retry/reconciliation, then apply the approved retention policy.

Add authenticated device register/revoke endpoints (for example, `PUT /v1/me/push-devices` and `DELETE /v1/me/push-devices/:id`), plus an authenticated notification-open resolver (for example, `POST /v1/notifications/:id/open`). The open resolver verifies recipient identity, current active membership, and shipment/conversation visibility before returning an allowed route; return a safe not-found response for unauthorized IDs. Ignore caller-supplied recipient identity. Do not expose FCM tokens from read APIs. Delivery is derived from persisted recipient notification rows, not a client endpoint that can name arbitrary shipment IDs or tokens.

## Failure, privacy, and security

- The worker makes bounded at-least-once submission attempts; FCM/device delivery is best-effort and may be missing, duplicated, delayed, or coalesced. In-app notification state remains durable and authoritative. Same-shipment Android replacement applies only when pushes are delivered; it does not prevent transport-level coalescing across shipments.
- Retry only transient errors, honor `Retry-After` within configured bounds, and define explicit provider timeout, maximum attempts, intent TTL, Android transport TTL/priority, and worker concurrency in the implementation plan. Invalid/unregistered tokens are revoked only when the returned token and ownership generation still match. Bound queue age, alert on poison rows, and provide safe redrive tooling without recording contents.
- Revalidate authorization and device ownership generation on each delivery attempt. Queued pushes are suppressed after account/membership/organization/shipment access is revoked or device ownership changes. A provider-accepted notification cannot be recalled; an OS may display a generic queued push after account switch/logout.
- FCM payloads are untrusted routing hints. The app never marks an item read or bypasses current authorization solely because a push arrived.
- Do not place OTPs, message text, auth/session data, payment details, or secrets in payloads, notification text, analytics, logs, or crash reports.
- Restrict registration/revocation/open endpoints with bearer authentication, validation, token rotation handling, rate limits, and audit-safe logs. Attempt server revocation before clearing auth and reconcile pending revocation on reconnect. Clear local pending routes, account-scoped caches, and visible app notifications on sign-out/account switch; never carry a notification route across an account change.
- If notification permission is denied, do not register the device for push; the in-app inbox continues working. Treat channel-level disablement as opt-out from tray display when the client next reports it.

## Testing and release gates

- API tests: authenticated registration/revocation/open resolver, caller identity cannot be spoofed, token rotation and account reassignment, duplicate registration, stale invalid-token cleanup cannot revoke newer token, intent/device snapshot atomicity with notification creation, no backfill to newly registered devices, per-device delivery outcomes, authorization/ownership recheck before retry, bounded retry/expiry and poison handling, no body/token leakage in logs/responses. Inject persistence failure, then perform an unrelated save and verify failed mutations do not leak source workflow state, event snapshots, device/intent/delivery maps, or leases; route existing payout/webhook mutations through the same coordinator and test overlapping HTTP, timer, and worker writes; test worker lease expiry and crash after provider acceptance.
- Flutter tests: permission/consent states, foreground local notification replacement identity, payload validation, notification-open resolver flow with no current organization selected, bounded pending route through initial sign-in, cancellation on logout/account switch/stale async auth generation, cold-start/background FCM taps via FCM-specific callbacks, local notification response and terminated-launch callbacks, explicit cancellation of existing tray notifications on logout/account switch, stale shipment access, unread refresh from the canonical API. Prove that background FCM and foreground local notifications use the same Android `(tag, id=0, channel)` identity; Android integration must verify the pinned SDK/plugin behavior. Keep Firebase initialization and callbacks guarded to Android so Flutter Web remains operational.
- Android integration tests on Android 12 and Android 13+: permission allow/deny/settings disable, foreground/background/terminated, force-stop caveat, FCM delivery and tap on a physical device with Google Play services, message/event coalescing, and more than one shipment.
- CI: Android APK build and unit/widget tests without Firebase production credentials; use a fake sender for API/outbox tests. Keep credentials only in an explicitly approved non-production secret environment for device delivery tests.
- Release: separate Firebase development and production apps; validate package ID, notification channel and permission UX, server service-account role, delivery metrics and runbook, persistence mode, single-writer constraint, and rollback behavior. Registration, enqueue, and sending feature flags default off; no historical backfill. Monitor outbox age, retry/permanent-failure rates, invalid tokens, provider latency, and suppressed deliveries. Rollback disables registration/sending while preserving canonical in-app notifications and safely expiring queued intents. Because current production uses FILE persistence, production FCM remains disabled by default; an explicitly approved single-process pilot may use `PUSH_ALLOW_FILE_PRODUCTION=1` with durable storage. PostgreSQL remains required before horizontal scaling or broader rollout. Do not enable production delivery until an owner has configured and approved production Firebase credentials.

## Cost

Firebase currently lists Cloud Messaging (FCM) as no-cost. Sending from the existing API and using the existing persistence/database avoids a separately billed Functions/Cloud Run service. Existing API/DB/egress/logging costs still apply; optional Firebase products are out of scope. Recheck Firebase pricing before launch.
