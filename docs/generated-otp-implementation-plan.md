## Accepted behavior for phase 1

1. Generate a six-digit numeric **string** on every newly issued challenge, including leading zeroes. Reuse the cryptographic generator. Remove `OTP_FIXED_CODE` as a runtime override; do not replace it with another universal code. A request within the resend cooldown reuses the existing challenge instead.
2. Keep the server setting `OTP_TTL_MS=600000` for ten minutes. An omitted setting uses the default. Explicit values must be finite positive integers whose resulting expiration timestamp is valid; reject invalid configuration during startup rather than silently falling back. Read the configuration once per app instance. Existing challenges retain their original deadline if configuration changes.
3. Return `{ challengeId, expiresAtUtcMs, retryAfterMs, debugCode? }`. Include `debugCode` only when the server has `OTP_DEBUG=1`. A request body/query parameter cannot enable debug delivery. Keep the generated code out of URLs and ordinary logs.
4. Verification continues to accept `{ phone, challengeId, code }`; compare against that challenge's generated code and retain current session/RBAC responses. A code is invalid at the exact expiration timestamp. A successful challenge is single use.
5. Resend policy: during the configurable cooldown, return the same pending challenge without generating another code or writing the store. After cooldown, a newly issued challenge supersedes prior pending challenges for the normalized phone. Phone and IP request windows return 429 with `retryAfterMs` and preserve any usable challenge. Two separately generated codes can legitimately coincide; challenge identity, not guaranteed numerical uniqueness, controls validity.
6. Preserve the current debug-delivery environment policy in this change; do not silently change deployment flags. Until a delivery provider exists, environments intended for this pilot flow need debug delivery enabled. Returning the code to the requesting client is a pilot convenience, not proof that the user possesses the phone.
7. Separate code generation/validation from delivery through a small delivery boundary. Implement the debug-response path now; add the WhatsApp adapter later without changing how the server validates codes. Keep the existing successful response shape; do not add an unused provider framework or real send operation in phase 1.

The user approved phase 1 implementation, including the resend policy and startup configuration validation above. This integration branch also combines the open dashboard PR #136. Session lifetimes, role assignments, carrier approval, payments, and registration eligibility remain outside this task.

## Database and rollout impact

- Core random generation and configurable expiry fit the existing `OtpChallengeRow` fields; no user/customer/role backfill is required.
- PostgreSQL stores `status` as a string, so a domain `SUPERSEDED` state does not itself require a database enum migration. Test FILE/DB serialization and loading explicitly.
- Existing pending challenges retain their original expiry during a rolling transition, including previously fixed codes. A fresh start creates a generated code and supersedes earlier pending challenges under the recommended policy. Already-issued login sessions remain valid.
- Do not modify production data to implement or test this plan. Use synthetic users and disposable stores/databases.
- The current persistence design needs a separate check before claiming cross-process atomic consumption. Multiple API replicas must share enforceable challenge state before WhatsApp production rollout; an in-memory guard alone is insufficient.

## Test matrix and manual acceptance

Automated checks must cover:

- Six numeric characters, including a controlled `000042` case; the generated value is the verified value. Do not assert that two random draws must differ, or that random output can never equal `123456`.
- `OTP_FIXED_CODE` cannot control runtime output after removal. `OTP_DEBUG` changes only response exposure.
- Default/custom TTL, invalid configuration, just before expiry, exact expiry, and just after expiry using a controlled clock.
- Wrong code, wrong normalized phone, unknown challenge, inactive/unknown user, replay, and superseded challenge.
- FILE/DB reload behavior and concurrent requests for the supported deployment topology.
- One start per driver sign-in; registration/deep-link fallback; customer sign-in; code clearing on resend; absent debug code; lead-zero entry; V1/V2/workflow compatibility.
- Existing RBAC, session, carrier, and payment behavior continues after generated-code login.

Manual sequence, after implementation:

1. Start a fresh synthetic local server with `OTP_DEBUG=1`, leaving `OTP_TTL_MS` unset. Request a code and inspect `{ challengeId, expiresAtUtcMs, debugCode }`. Expect a generated six-digit string and an approximately ten-minute deadline.
2. Enter/use the returned code, not a memorized value. Verify login and the same role/organization access as before.
3. On a fresh challenge, submit a different six-digit value and confirm no session is created. Submit the correct value before expiry and confirm success, then replay the challenge and confirm rejection.
4. Request another challenge and then resend. Verify the older challenge is invalid and the newest response can complete login. Inspect the driver network requests: opening the OTP screen must not automatically create a second challenge if one was already supplied.
5. Restart only the synthetic server with a short local override such as `OTP_TTL_MS=5000`; request a fresh code, wait over five seconds, and verify expiration. Restore the default afterward. The exact timestamp boundary belongs in automated tests, not manual stopwatch testing.
6. In an isolated test configuration, set `OTP_DEBUG=0` and confirm start responses and UI contain no debug code. No real delivery is expected until phase 2. Verify this using API/provider mocks rather than reading a live code from storage.
7. Repeat driver/customer and web login flows at desktop and mobile widths. Retest V1/V2 switching and shipper POD access once PR #136 is present.

## OTP resend cooldown and request limits (feature follow-up)

This follow-up keeps the current OTP challenge valid during a configurable resend cooldown and adds request limits to address unauthenticated challenge invalidation and write amplification. Defaults: `OTP_RESEND_COOLDOWN_MS=30000`, `OTP_PHONE_START_LIMIT=5`, `OTP_PHONE_START_WINDOW_MS=3600000`, `OTP_IP_START_LIMIT=30`, and `OTP_IP_START_WINDOW_MS=600000`. A retry during cooldown returns the same challenge and does not persist a second full-store snapshot. A phone-limit or IP-limit rejection returns HTTP 429 with `otp_rate_limited`, `retryAfterMs`, and a `Retry-After` header. Client screens disable resend and show the countdown; changing the phone resets that local challenge state.

The API trusts `X-Forwarded-For` only with `OTP_TRUST_PROXY=1`; enable this for the Render proxy. IP counters are per process, so a future multi-instance deployment needs shared rate-limit storage. No database schema migration is required because per-phone issuance history uses existing challenge rows; IP counters are intentionally ephemeral. This follow-up is implemented and tested on the OTP feature branch. Do not merge to `main` until the user confirms.
