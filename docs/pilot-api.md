## Pilot API resources (Driver app first)

This document defines the **first concrete API resources** for the Flutter pilot, optimized for **solo owner-operators modeled as a “carrier org of one”**.

### Conventions
- **Money**: integer **paise** (₹1 = 100 paise).
- **IDs**: opaque strings generated by the server.
- **Legacy field naming**: `AnchorTrip.carrierId` is the **Organization id** for carrier-side entities (kept for backwards compatibility with earlier MVP code).
- **Pilot auth**:
  - Use **OTP** to obtain an **access token**
  - Send `Authorization: Bearer <accessToken>` on protected routes
  - Dev escape hatch: set `ALLOW_X_USER_ID=1` and pass `x-user-id` (local only)

### Server env vars (pilot)
- **`AUTH_SECRET`**: required (min 16 chars). Used to sign access tokens.
- **`OTP_DEBUG=1`**: returns the generated six-digit `debugCode` from `otp/start` for local testing. Codes are random; this setting controls delivery only. **`OTP_TTL_MS`** defaults to `600000` (ten minutes); an explicit value must be a positive safe integer that produces a valid expiration timestamp, or startup fails. **`OTP_RESEND_COOLDOWN_MS`** defaults to `30000` (30 seconds). **`OTP_PHONE_START_LIMIT` / `OTP_PHONE_START_WINDOW_MS`** default to 5 newly issued challenges per phone per hour. **`OTP_IP_START_LIMIT` / `OTP_IP_START_WINDOW_MS`** default to 30 start requests per IP per 10 minutes.
- **`CONVERSATION_REPLY_WINDOW_DAYS`**: optional nonnegative number of days to allow replies after a shipment first enters `DELIVERED` or `FAILED_CARRIER_REFUNDED` (default **14**). Existing terminal shipments without reliable transition timestamps are read-only.
- **`CONVERSATION_SENDS_PER_MINUTE`**: optional per-user, per-conversation send limit (default **20**, maximum **120**).
- **`ALLOW_X_USER_ID=1`**: allows the old header-based auth (not for real pilots).
- **`ENABLE_LEGACY_DEMO_SURFACE=1`**: enables legacy unauthenticated admin/demo write routes in production. Leave unset for hosted pilots.
- **`FREIGHT_PAISE_PER_KM_SMALL`**, **`FREIGHT_PAISE_PER_KM_MEDIUM`**, **`FREIGHT_PAISE_PER_KM_LARGE`**: paise per km defaults (see `apps/api/src/config.ts`).
- **`FREIGHT_MIN_GROSS_PAISE`**: optional minimum gross paise when distance is priced.
- **`PERSISTENCE`**: omit or **`FILE`** (default) — JSON snapshot via **`DATA_FILE`** (path). Set **`DB`** for Postgres (**`DATABASE_URL`** required); run `cd apps/api && npx prisma db push` once. Full-store snapshot load/save, not row-level repos yet.
- **`PUSH_ALLOW_FILE_PRODUCTION=1`**: explicit opt-in for the FCM sender with `NODE_ENV=production` and FILE persistence. Leave unset by default; use only for an approved single-process pilot with durable storage. PostgreSQL remains required before horizontal scaling or broader rollout.
- **`PAYMENT_PROVIDER`**: omit or **`MOCK`** — payment is **`CAPTURED`** at booking (tests + local demos). **`RAZORPAY`** — Razorpay test/live keys; authorize at checkout, capture at POD (see below).
- **`RAZORPAY_KEY_ID`**, **`RAZORPAY_KEY_SECRET`**: Standard checkout + server APIs (Flutter uses **key id**; server gets **`razorpayKeyId`** on book response — must match checkout key).
- **`RAZORPAY_WEBHOOK_SECRET`**: Razorpay dashboard webhook secret; required for **`POST /v1/payments/razorpay/webhook`**.
- **`PAYOUTS_MODE`**: omit or **`BOOKKEEPING`** (default) — `POST /payout-batches/run` only marks ledger lines **`PAID`** (no money moves; MVP bookkeeping). **`RAZORPAYX`** — creates a real **RazorpayX payout per carrier** (reuses `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`, test keys in dev). Carriers without a fund account are skipped (lines stay `ACCRUED` to retry); errored transfers are marked `FAILED` and retried next run. `POST /payout-batches/run`, `GET /payout-batches`, and `GET /carriers/:id/ledger` require an **Ops Admin/Agent** bearer token.
- **`RAZORPAYX_ACCOUNT_NUMBER`**: source account number from the RazorpayX dashboard; required when `PAYOUTS_MODE=RAZORPAYX`.
- **`RAZORPAYX_PAYOUT_MODE`**: optional transfer rail — `IMPS` (default) | `NEFT` | `RTGS` | `UPI`. To register a carrier for payouts, call `POST /v1/pilot/carrier/payout-setup` with `accountHolderName`, `ifsc` and `accountNumber`, all required in every payout mode (a blank one is refused with 400 `invalid_payout_profile`); in RAZORPAYX mode the server then creates a RazorpayX contact + fund account and stores the ids on the org.

### Data model (persistence)

The API keeps an in-memory **`Store`** and persists it either to **`DATA_FILE`** (JSON) or to Postgres (**`PERSISTENCE=DB`**) after mutating routes. DB mode still uses a full-store snapshot for most existing entities; communication rows are upserted without being deleted/recreated on unrelated writes. Run `cd apps/api && npx prisma db push` to apply schema changes. Operate a single API writer until the broader snapshot path has concurrency control. Entities match the MVP:

- `Organization` (`CARRIER_SOLO` | `CARRIER_FLEET` | `CUSTOMER` | `CARRIER_LEGACY`)
- `User` (phone + fullName)
- `Membership` (user ↔ org, role)
- `Vehicle` (owned by org)
- `DriverProfile` (pilot assumes **one profile per user**)
- Shipment lifecycle: `PENDING_CARRIER_ACCEPT` (customer booked) → carrier **accept** → `BOOKED` → driver POD → `PENDING_RELEASE` → ops release → `DELIVERED`
- Anchor trip lifecycle: `OPEN` / `FULL` → carrier **start** → `IN_PROGRESS` (enables live GPS to customers) → `COMPLETED`. Before the start, a trip with no booking can go to `CANCELLED`, and one with bookings to `CANCEL_REQUESTED`, then back to `OPEN` / `FULL` (withdrawn) or on to `CANCELLED` once Finance has cancelled its last booking (see "Cancelling a trip" below)
- `OtpChallenge` / `AuthSession` (pilot login)
- `Payment`: `provider` **`MOCK` | `RAZORPAY`**, **`status`** `CREATED` → `AUTHORIZED` → `CAPTURED` (or `FAILED` / `REFUNDED` / `HOLD_RELEASED` / `CAPTURED_AFTER_CANCEL`), **`razorpayOrderId`** / **`razorpayPaymentId`** when applicable. `HOLD_RELEASED`: the shipment was cancelled while the payment was only authorized, so nothing was sent to Razorpay (see `fail-refund` below). `CAPTURED_AFTER_CANCEL`: Razorpay reported a capture after the shipment was cancelled (see the webhook below); **`capturedAfterCancelRazorpayPaymentId`** (`FINANCE` only) is that capture's Razorpay payment id, kept beside `razorpayPaymentId`, which stays the earlier one. Finance marks each such capture with `mark-refunded` once refunded in Razorpay, and the payment becomes `REFUNDED` when none is left. An unpaid booking (`CREATED` or `FAILED`) that is cancelled is marked `REFUNDED`, as before

### Notifications and shipment conversations

All endpoints below require the OTP bearer token and selected active organization. SHIPPER and CARRIER access is limited to active members of the shipment's customer/carrier organization; FINANCE, ADMIN, and OPS receive no default conversation access. All active eligible shipper and carrier members receive in-app alerts for booking, carrier acceptance, trip start/completion, POD submission/acceptance, payment-state changes, a shipment cancelled by Finance (`shipment.cancelled`, alongside the payment-state alert), a shipment closed because its trip started before it was paid for (`shipment.left_behind`, shipper logins only; see the start route), a booking closed because it was not paid within 30 minutes (`shipment.booking_expired`, shipper logins only), and new messages. A cancelled or closed shipment hears no trip start or completion. Alerts use role-specific English copy and do not include payment amounts or user-authored message text.

- `GET /v1/notifications?limit=30&before=<createdAtUtcMs:id>` returns `{ notifications, nextCursor, unreadCount }`; `limit` is clamped to 1–100.
- `GET /v1/notifications/shipments?limit=30&before=<opaque-cursor>` returns one row per active shipment with `{ shipments: [{ shipmentId, shipmentReference, latestAtUtcMs, unreadCount }], nextBefore, unreadCount, notificationSequence }`. `shipmentReference` uses the external load ID when present, otherwise a short shipment ID. The inbox heading and preview are generic; it does not return message text or payment values. Reuse `nextBefore` unchanged while paging a snapshot; refresh to include newer activity.
- `PATCH /v1/notifications/:notificationId/read` marks the current user's notification read.
- `GET /v1/shipments/:shipmentId/conversation/messages?limit=50&beforeSequence=<n>` returns `{ conversation, messages, nextBeforeSequence, canSend }`. Message history is ordered by sequence; `canSend` is server-authoritative.
- `GET /v1/shipments/:shipmentId/conversation/timeline?limit=50&before=<opaque-cursor>` returns `{ conversation, items, nextBefore, readWatermark, canSend }`. `items` contains chronological `message` and recipient-specific workflow `event` items; a message sorts before an event at the same stored millisecond. The cursor is recipient/org/shipment/page-size scoped and retains the original read snapshot.
- `POST /v1/shipments/:shipmentId/conversation/read` accepts `{ "readWatermark": { "notificationSequence": n, "messageSequence": n } }`. It acknowledges only this user's events and messages through that timeline snapshot, so later arrivals stay unread. Repeating the request is safe.
- `POST /v1/shipments/:shipmentId/conversation/messages` accepts `{ "body": "...", "clientRequestId": "..." }`. Text is limited to 4,000 characters. Repeating the same key and body returns the original message; reusing a key with changed text returns HTTP 409 `idempotency_conflict`. New sends after the reply deadline return HTTP 409 `conversation_read_only`; previously accepted sends remain retryable after closure. The app words that refusal "Messages are closed for this shipment." for a shipper, "Messages are closed for this booking." for a carrier, "Messages are closed." for anyone else, and loads the conversation again so its closed banner shows at once. Throttling returns HTTP 429 `conversation_rate_limited` with `retryAfterMs` and `Retry-After`.
- `POST /v1/shipments/:shipmentId/conversation/escalations` requests time-limited OPS access with `{ "granteeUserId", "reason", "canRead", "canSend", "expiresAtUtcMs" }`. A designated approver approves or denies using `POST /v1/conversation-escalations/:grantId/approve` or `/deny`; grant holders' access is scoped, expires, and is audited. `POST /v1/conversation-escalations/:grantId/revoke` revokes an approved grant. OPS access does not override the terminal reply deadline.

The API stores messages and notifications in the configured persistence backend. It does not provide push delivery or WhatsApp delivery in this phase. Local drafts are encrypted by Flutter secure storage and scoped to the signed-in user, organization, and shipment. See [the notification and two-way communication design](notification-and-two-way-communication-design.md) and [phase implementation plan](notification-communication-implementation-plan.md).

### Endpoints

#### `POST /v1/auth/otp/start`
Body:
```json
{ "phone": "9876543210" }
```

Response:
```json
{
  "challengeId": "otp_...",
  "expiresAtUtcMs": 1234567890,
  "debugCode": "482019"
}
```

Note: `debugCode` is only present when `OTP_DEBUG=1`. A start request during the 30-second cooldown returns the same challenge and code without persisting another store snapshot; no new code is generated. After the cooldown, a new random code is issued and the prior pending challenge is superseded, subject to the phone issuance limit. Requests are also limited by client IP, including requests during cooldown. A limit response uses HTTP 429 with `{ "error": "otp_rate_limited", "retryAfterMs": ... }` and a `Retry-After` header. The API trusts `X-Forwarded-For` only when `OTP_TRUST_PROXY=1`; otherwise it uses the direct socket IP. Keep `OTP_TRUST_PROXY=1` for the Render deployment that supplies the forwarding header. No external delivery channel is implemented yet; pilot login requires debug delivery. Retry an incorrect code before its deadline; request a new code after expiration.

#### `POST /v1/auth/otp/verify`
Body:
```json
{
  "phone": "9876543210",
  "challengeId": "otp_...",
  "code": "482019"
}
```

Response:
```json
{
  "user": { "...": "..." },
  "accessToken": "<jwt-like signed token>",
  "session": { "...": "..." }
}
```

One code takes five wrong entries: the fifth answers `400 { "error": "otp_too_many_wrong_codes" }` and the code stops working (a later check answers `otp_challenge_invalid`), so the person requests a new code. The app words it "Too many wrong codes. Send a new code."

Code checks and the three sign-up routes (`/v1/pilot/driver/register`, `/v1/pilot/customer/register`, `/v1/pilot/customer/users/register`) have a per-IP limit only when `OTP_TRUST_PROXY=1`, because without it the socket IP may be the proxy's, shared by every visitor. Without it they rely on the five-wrong-codes limit per code and the per-phone limits; code requests (`otp/start`) keep their per-IP limit either way. A code check over its limit answers `429 otp_rate_limited` with `retryAfterMs`, which the app words "Too many tries. Please wait N minutes and try again.", N rounded up.

On the three sign-up routes, `fullName` and `orgDisplayName` can have at most 100 characters and `phone` at most 20, after trimming. A longer one is refused and nothing is saved: `400 { "error": "invalid_fullName", "detail": "A name can have at most 100 characters.", "field": "fullName" }`, and the same for `invalid_orgDisplayName` ("A company name can have at most 100 characters.") and `invalid_phone` ("A phone number can have at most 20 characters."). The app shows the `detail` and its fields stop at those lengths. Each phone gets 5 sign-up tries an hour, and each IP 30 in 10 minutes when `OTP_TRUST_PROXY=1`; a try refused for its IP does not count against the phone. Over a limit answers `429 { "error": "rate_limited", "retryAfterMs": ... }` with a `Retry-After` header, which the app words "Too many tries. Please wait N minutes and try again.", N rounded up.

#### `POST /v1/pilot/driver/register`
Creates:
- `User`
- `Organization(kind=CARRIER_SOLO)`
- `Membership(role=OWNER_DRIVER)`
- `Vehicle`
- `DriverProfile`

Body:
```json
{
  "fullName": "Ravi Kumar",
  "phone": "9876543210",
  "orgDisplayName": "Ravi Transport",
  "vehicleRegistrationNumber": "HR26AB1234",
  "vehicleClass": "MEDIUM",
  "vehicleCapacityKg": 5000,
  "transporterId": "29ABCDE1234F1Z5"
}
```

`transporterId` is optional: the carrier's GSTIN, or the TRANSIN the e-way bill portal gives a transporter with no GST registration. Spaces are removed and letters upper-cased; it must then be two digits followed by 13 letters or digits, or the sign-up is refused and nothing is registered: `400 { "error": "invalid_transporter_id", "detail": "A transporter ID is 15 letters and digits, starting with two digits: your GSTIN, or the TRANSIN from the e-way bill portal. Leave it empty if you do not have one.", "field": "transporterId" }`. Left out, `null` or blank means none. See "Carrier transporter ID" below.

#### `POST /v1/pilot/driver/login`
Legacy demo helper that returns the same “bundle” as register, for a known phone.
It is disabled when `NODE_ENV=production` unless `ENABLE_LEGACY_DEMO_SURFACE=1`.

Body:
```json
{ "phone": "9876543210" }
```

#### `GET /v1/pilot/me`
Headers:
- `Authorization: Bearer <accessToken>`

Returns the signed-in user, memberships, organizations, vehicles on those orgs, and `driverProfile` (if any). In a carrier context the carrier office (`OWNER`, `OWNER_DRIVER`, `DISPATCHER`) also gets its own organization's `transporterId` when it has one; a `DRIVER` does not.

#### `PATCH /v1/pilot/me/vehicle`
Update the signed-in driver's **primary vehicle** (registration, class, and/or capacity). Requires Bearer and an existing driver profile. Partial updates are allowed — omit a field to leave it unchanged.

Body (any subset):
```json
{
  "vehicleRegistrationNumber": "HR26CD5678",
  "vehicleClass": "MEDIUM",
  "vehicleCapacityKg": 4500
}
```

Response:
```json
{
  "vehicle": { "id": "veh_...", "orgId": "org_...", "registrationNumber": "HR26CD5678", "vehicleClass": "MEDIUM", "capacityKg": 4500, "createdAtUtcMs": 123 },
  "driverProfile": { "userId": "usr_...", "orgId": "org_...", "primaryVehicleId": "veh_...", "createdAtUtcMs": 123 }
}
```

A `DRIVER` cannot change a truck while a trip that is not `COMPLETED` or `CANCELLED` names it (`assignedVehicleId`; a `CANCEL_REQUESTED` trip still holds it), because that is the truck the trip's shippers read: `409 { "error": "truck_on_unfinished_trip", "detail": "This truck is on a trip that is not finished. Ask your carrier to change it." }`, whichever field is sent. Owners, owner-drivers and dispatchers are not refused. The registration number is trimmed and can have at most 20 characters, here and when a carrier registers (`POST /v1/pilot/driver/register`) or invites a driver (`POST /v1/pilot/carrier/drivers/invite`): `400 { "error": "invalid_vehicleRegistrationNumber", "detail": "A truck number can have at most 20 characters.", "field": "vehicleRegistrationNumber" }`. There is no letters-and-digits rule, so forms like `TEST-A` stay valid.

#### `GET /v1/pilot/anchor-trips`
Headers:
- `Authorization: Bearer <accessToken>`

Response:
```json
{
  "trips": [
    {
      "id": "trip_...",
      "carrierId": "<orgId>",
      "originCity": "Gurugram",
      "destCity": "Jaipur",
      "windowStart": "2026-04-24T00:00:00+05:30",
      "windowEnd": "2026-04-25T23:59:59+05:30",
      "vehicleClass": "MEDIUM",
      "capacityKg": 1000,
      "reservedKg": 0,
      "status": "OPEN",
      "createdAtUtcMs": 1234567890
    }
  ]
}
```

Trips are limited to **carrier orgs** your user belongs to (`CARRIER_SOLO`, `CARRIER_FLEET`, `CARRIER_LEGACY`), newest first. A login whose membership is **`DRIVER`** gets only the trips whose `assignedDriverUserId` is them, and for now a trip that names no driver and that they started (see "Truck and driver per trip" below); with neither the list is empty.

#### Truck and driver per trip

A trip may name one truck and one driver: `assignedVehicleId` and `assignedDriverUserId`, both optional. Carrier and ops responses also carry `assignedTruckNumber` (the truck's registration in the e-way bill portal's form, see "Truck numbers in the portal's form" below) and `assignedDriverName`; shippers, public trip lists and ERP responses get none of the four. A trip published by a solo owner-operator (the `OWNER_DRIVER` of a `CARRIER_SOLO` organization) names that person and their primary vehicle by itself. Inviting a driver or dispatcher makes the organization `CARRIER_FLEET`, and from then on trips its owner-driver publishes stay unassigned. Trips from before this change stay unassigned.

**Who sees what.** Owners, owner-drivers and dispatchers see all of their carrier's trips and shipments. A `DRIVER` sees only trips naming them and the shipments on those trips on these routes: the trip list and detail, start, complete and location, the carrier shipment list (with or without `anchorTripId`), accept, proof of delivery, tracking, the shipment conversation, the notification list, the grouped inbox, mark-read and notification open. A trip or shipment outside that answers `404`, as for another carrier. New notifications go only to the driver named on the trip, and a queued push is dropped at send time if the trip names someone else by then. Not yet limited: `GET /v1/pilot/me`, which lists every truck of the carrier. In database mode the grouped inbox can return a short page, and its `unreadCount` still counts groups hidden from a driver.

**Trips from before this change.** A trip that names no driver stays with the `DRIVER` who started it (`startedByUserId`) on every route above, in any status, so a driver mid-route at deploy keeps sending location, confirming delivery and completing, and still sees the trip and its shipments once it is complete. It leaves their list only if the office assigns it to someone else, which is possible until it is complete; a completed one cannot be assigned, so it stays with its driver. A trip that was never started has no starter, so one that is `OPEN` or `FULL` and names no driver is visible to no driver. Trips started before assignments existed name nobody; the driver who started one keeps it. Before go-live the carrier office should assign every open trip; in-progress trips started by a driver keep working until assigned.

**A driver never sees carrier earnings (owner decision, 15 Oct 2026).** A `DRIVER` membership does not hold `payment.read`, so `GET /v1/pilot/carrier/earnings`, `/ledger` and `/payout-batches` answer `403` for a driver; owners, owner-drivers and dispatchers keep them. No response to a `DRIVER` carries what the carrier earns or when it is paid: `netToCarrierPaise`, `totalNetToCarrierPaise`, `pendingAccruedPaise`, `paidPaise`, the payout dates `firstPayoutEligibleAtUtcMs`, `payoutBatchCutoffUtcMs`, `paidAtUtcMs` and `cutoffUtcMs`, and the payment hold `paymentReady` and `paymentHoldUntilUtcMs`, whatever the route. Owners, owner-drivers, dispatchers, finance and ops keep the ones they had. A driver is never notified of a payment status change (`payment.status_changed`).

**Each side gets only its own amount (owner hard rule, 21 Oct 2026).** No response, notification, push, conversation event or ERP payload to a carrier login carries the shipper's price (`grossPaise`, payment `amountPaise`), `commissionPaise` or a fee rate. None to a shipper login or a shipper's ERP carries `netToCarrierPaise`, `commissionPaise`, earnings, ledger or the payout dates `firstPayoutEligibleAtUtcMs` and `payoutBatchCutoffUtcMs`; a shipper keeps its own payment hold, `paymentReady` and `paymentHoldUntilUtcMs`. The serializer removes these per side after every branch. NaviG8r's own logins (ops, finance, admin) keep both.

**`POST /v1/pilot/anchor-trips/:tripId/assignment`** (permission **`trip.assign`**: carrier `OWNER_DRIVER`, `OWNER`, `DISPATCHER`, never `DRIVER`). Body `{ "vehicleId": "...", "driverUserId": "..." }`. Both must belong to the trip's carrier: the vehicle's `orgId` is the trip's `carrierId`, and the driver is an active member with role `DRIVER`, `OWNER_DRIVER` or `OWNER`. Replaces any earlier assignment. Response `200 { "trip": {...}, "driverBusy": false }`; `driverBusy` is `true` when that driver is already named on another trip that is `IN_PROGRESS` (a warning, the assignment is saved). Refusals: `400 { "error": "invalid_trip_assignment", "detail": "a sentence", "field": "vehicleId" | "driverUserId" }`, `409 trip_completed`, `409 trip_cancelled`, `403` for a driver, `404` for another carrier's trip. Audit row `TRIP_ASSIGNED` on the trip, states `UNASSIGNED` or `ASSIGNED` only. When the truck changes from one truck to another (the first truck chosen tells nobody), each shipper login on a `BOOKED` shipment whose bill names a different truck (portal form) gets a notification: `eventKey: "eway_bill.truck_changed"`, title "The truck on your trip is different from your e-way bill", body "[carrier] set the truck on this trip to [truck]. Your e-way bill has [truck on the bill]. Ask [carrier] which is right. If the bill is wrong, fix it on the portal, then here." A carrier with no name reads "Your carrier" and "your carrier", never its id. Earlier unread notices of this kind for that shipment are marked read first, so one stays unread. At most one is sent per shipment in 6 hours (owner, 23 Oct 2026): within 6 hours of the last one, a further change sends nothing and marks nothing read, since the shipment screen always shows the trip's latest truck. When the truck goes back to the one on the bill, that shipment's unread ones are marked read and nothing is sent.

**`GET /v1/pilot/carrier/fleet`** (permission `trip.assign`). The pickers' choices for the caller's own carrier: `{ "vehicles": [{ "id", "registrationNumber", "vehicleClass" }], "drivers": [{ "userId", "displayName" }] }`. No phone numbers. `GET /v1/pilot/me` already lists the carrier's vehicles but not its people, so this route was added.

#### Cancelling a trip (owner decision, 19 Oct 2026)

All three routes take permission **`trip.assign`** (carrier `OWNER_DRIVER`, `OWNER`, `DISPATCHER`; never `DRIVER`, ops or finance) and answer `200 { "trip": {...} }`, `403` for a driver of the trip, `404` for another carrier's trip. Each writes an audit row `TRIP_STATUS_CHANGED` with the old and new status, as Start does. "Bookings" means any shipment on the trip that is `PENDING_CARRIER_ACCEPT` (paid, unpaid or failed payment) or `BOOKED`.

- **`POST /v1/pilot/anchor-trips/:tripId/cancel`**: a trip with no booking, from `OPEN` or `FULL`, becomes `CANCELLED`. Refusals: `409 { "error": "trip_has_bookings", "detail": "This trip has bookings, so it cannot be cancelled here." }`, `409 trip_not_cancellable` for any other status. Asking again for a cancelled trip answers `200` with nothing changed.
- **`POST /v1/pilot/anchor-trips/:tripId/cancel-request`**: body `{ "reasonCode": "TRUCK_UNAVAILABLE" | "DRIVER_UNAVAILABLE" | "ROUTE_CHANGED" | "OTHER", "note"?: "up to 500 characters" }`. A trip with bookings, from `OPEN` or `FULL`, becomes `CANCEL_REQUESTED`. Refusals: `409 trip_has_no_bookings` (use `cancel`), `409 trip_not_cancellable`, `400 { "error": "invalid_cancel_request", "detail": "a sentence", "field": "reasonCode" | "note" }`. Asking again answers `200` and keeps the first reason. The audit row's `reasonCode` is the reason code. The audit row has no place for free text, so the trimmed note is kept only on the trip, in `cancelRequest: { reasonCode, note?, requestedAtUtcMs }`, which only operations staff (`OPS`, `FINANCE`, `ADMIN`) get in responses; carriers, shippers, public lists and ERP responses never do. In database mode `cancelRequest` is not saved (the trip table has no column for it), so the reason and note would be lost on restart; no environment runs database mode today.
- **`POST /v1/pilot/anchor-trips/:tripId/cancel-request/withdraw`**: `CANCEL_REQUESTED` goes back to `FULL` when the bookings fill the trip, `OPEN` otherwise, and `cancelRequest` is removed. Withdrawing a request already withdrawn answers `200`; any other status is `409 no_cancel_request`.

A `CANCEL_REQUESTED` or `CANCELLED` trip is left out of `GET /anchor-trips` (it is still readable by id) and of the eligible-trip search, takes no booking (`400 anchor_trip_not_open`), and cannot be started (`trip_not_startable`), completed or sent a location. A `CANCELLED` trip cannot be assigned (`409 trip_cancelled`) and no longer holds its truck. A booking on a `CANCEL_REQUESTED` trip cannot be accepted (`409 { "error": "trip_cancel_requested", "detail": "This trip's carrier asked NaviG8r to cancel it, so it cannot take this booking now." }`), and its delivery cannot be confirmed (`POST /shipments/:id/driver-pod`: `409 trip_cancel_requested`, "This trip's carrier asked NaviG8r to cancel it, so delivery cannot be confirmed now."). Both sentences go to drivers as well as the office, so neither tells the reader to withdraw; the app shows the office its own "Withdraw the request first." wording, and a driver "Your office asked NaviG8r to cancel this trip.", before either taps. POD is refused rather than ending the trip, because a delivered load means the trip ran; so a requested trip ends only through Finance's cancels, below.

**When a requested trip ends.** Finance cancels each booked shipment with `POST /shipments/:id/fail-refund` (on `/ops/beta` under "Trip cancel requests"). When the last booking on a `CANCEL_REQUESTED` trip is cancelled, the server sets the trip to `CANCELLED` in the same request, with an audit row by the Finance user. There is no separate "cancel trip" action for ops. `fail-refund` reopens only a `FULL` trip; it never reopens a `CANCEL_REQUESTED` or `CANCELLED` one. The "Trip cancel requests" card sends body `{ "fromCancelRequest": true }`; with it, the server refuses unless the shipment's trip is still `CANCEL_REQUESTED`: `409 { "error": "cancel_request_withdrawn", "detail": "The carrier withdrew this request. Nothing changed." }`. Without it (the general fail-refund action), nothing changes.

#### `GET /ops/trip-cancel-requests`

Operations staff only (`403` for anyone else). `{ "requests": [{ "trip": {...with carrierDisplayName and cancelRequest}, "shipments": [{ "shipment": {...}, "payment": {...}, "settledOutsideNaviG8r": false }] }] }`: every `CANCEL_REQUESTED` trip, oldest request first, with the bookings still on it, oldest first. `settledOutsideNaviG8r` is `true` for an ERP `erp_preauthorized` booking (Razorpay provider, `AUTHORIZED`, no Razorpay payment or order id): there is no Razorpay hold, `fail-refund` refuses it, and the card shows "Settled outside NaviG8r" with Cancel shipment off and "This load's payment is settled outside NaviG8r through the partner's system, so it cannot be cancelled here. Ask the carrier to withdraw the request, or settle it with the partner." There is no cancel path for these in NaviG8r. Beside it, `"collectedAfterCancel": [{ "shipment": {...}, "payment": {...} }]`: every payment marked `CAPTURED_AFTER_CANCEL` (see the webhook below), oldest first. Every staff role sees this list, to triage; the card tells Finance "Money collected after cancel. Refund it in the Razorpay dashboard, then mark it refunded here." with the Razorpay order and captured payment ids, and anyone else "Money collected after cancel. Finance refunds this in the Razorpay dashboard." The usual field rules apply: of the staff roles, only `FINANCE` gets the shipment's `grossPaise` and the payment's `amountPaise`, `razorpayOrderId` and `capturedAfterCancelRazorpayPaymentId`.

#### `POST /shipments/:id/mark-refunded`

`FINANCE` only (`payment.refund`; `403` for anyone else). Body `{ "razorpayPaymentId": "pay_..." }`, required: the Razorpay payment Finance refunded, which must be the payment's `capturedAfterCancelRazorpayPaymentId`. Records that Finance refunded it in the Razorpay dashboard; nothing is sent to Razorpay. The audit row `PAYMENT_MARKED_REFUNDED` by the Finance user (resource the shipment, `previousState` `CAPTURED_AFTER_CANCEL`, `newState` the payment's status after, `razorpayPaymentId` the id marked) is visible to `FINANCE` in `GET /v1/audit`. If another capture on the shipment is still to refund (an id on a `PAYMENT_AFTER_CANCEL` row with `reasonCode` `CAPTURED` and on no `PAYMENT_MARKED_REFUNDED` row), the payment stays `CAPTURED_AFTER_CANCEL` with the oldest such id in `capturedAfterCancelRazorpayPaymentId` and stays in `collectedAfterCancel`; otherwise it becomes `REFUNDED`. `200 { "payment": {...} }`; marking an id already marked answers `200` and changes nothing; a payment not waiting is `409 { "error": "payment_not_captured_after_cancel", "detail": "This payment is not waiting for a refund after a cancel." }`; a missing id, or one that is not the waiting one, is `409 { "error": "refund_payment_id_mismatch", "detail": "This is not the payment waiting for a refund. Reload the page." }`. Once `REFUNDED` the payment leaves `collectedAfterCancel`, and the shipper's screen reads as any refunded booking. On `/ops/beta` it is "Mark refunded in Razorpay…", which first asks in the page "Mark payment [id] of [amount] as refunded? Do this only once you have refunded it in the Razorpay dashboard. The shipper's screen then says it is refunded. This can't be undone from the console." (Not yet, focused · Mark refunded), sends the id the card shows, then shows "Marked refunded by you at [time]. This leaves the list on the next reload." and drops the row from the card's counts. When another capture is still to refund it shows instead "Marked refunded by you at [time]. Razorpay also collected payment [id] on this shipment. It shows here to refund on the next reload." and the counts stay.

**Database mode:** two nullable columns on the trip table must exist first, or the API will not start in database mode at all: at boot it loads every trip row with every column, and that load fails without them, so the process exits before serving anything. Applying `ALTER TABLE "AnchorTripRow" ADD COLUMN "assignedVehicleId" TEXT, ADD COLUMN "assignedDriverUserId" TEXT;` by hand is a merge gate for every database-mode service. `render.yaml` sets no `PERSISTENCE` for its API services, so as written they run in file mode and need nothing; a service given `PERSISTENCE=DB` anywhere else does.

Shipments carry a read-only `assignedTruckNumber` (the trip's truck, same form) for shipper, carrier and ops logins, never for finance, admin or ERP callers. The e-way bill cards compare it with the bill's `truckNumber`, both sides put through the portal's form first.

**Truck numbers in the portal's form (16 Oct 2026).** One rule, in the API (`portalTruckNumber` in `tripAssignmentRules.ts`) and in the app (`portalTruckNumber` in `eway_bill_words.dart`): upper case, everything but letters and digits removed; then, if it is two letters, one or two digits, zero to three letters and one to four digits, the first digits are padded to two and the last to four. The first digits are never a lone 0: starting with 0, they are two. With no letters between the two groups of digits, a space or other mark typed between them is where the first group ends: `UP 32 345` becomes `UP320345` and `UP 1 345` becomes `UP010345`. With none typed, a first digit from 1 to 9 stands alone, so `UP1345` also becomes `UP010345`, while `KA01123` becomes `KA010123`. `KA01AB1234` stays. Any other shape (temporary numbers, Bharat series, defence, foreign) is only cleaned. The bill's own `truckNumber` is stored as typed (spaces and hyphens removed, upper case); only the comparison goes through the rule. So a bill truck typed as `UP 32 345` is stored as `UP32345`, compared as `UP032345`, and shown as different from a trip truck `UP320345`; the truck forms start with the trip's truck in the portal's form, which avoids it. The practice portal keeps its own cleaner, which removes spaces and hyphens and pads nothing.

#### `POST /v1/pilot/anchor-trips/:tripId/start`
Carrier explicitly starts a load (`OPEN`/`FULL` → `IN_PROGRESS`). Requires at least one **`BOOKED`** shipment on the trip (carrier must accept bookings first). Enables GPS pings and customer live tracking.

Every `BOOKED` shipment on the trip must have a final e-way bill (owner, 23 Oct 2026): `kind: "NOT_NEEDED"`, or `kind: "BILL"` with a truck number equal to the trip's truck (both in the portal form), a `validUntilUtcMs` still ahead, and no ops `check.result` of `PROBLEM`. NaviG8r does not check every bill by hand: this reads what was entered, and a problem NaviG8r found when it looked a bill up on the portal also blocks the start. Deleted shipments are skipped, here and in the payment and accepted-booking checks. A bill with a truck but no `validUntilUtcMs` reads as `truck_missing`. Otherwise `409 { "error": "eway_bill_not_ready", "shipments": [{ "shipmentId", "shipperName", "reason" }] }`, one entry per blocking shipment, `reason` one of `no_bill`, `truck_missing`, `truck_differs` (also when the trip has no truck), `expired`, `problem`, checked in that order. Shipper names only, which every carrier login already sees; no money. The trip is unchanged. A refusal tells no shipper (owner, 23 Oct 2026): the office uses the reminder route below. Rule in `apps/api/src/ewayBillStartGate.ts`; the app mirrors it in `eway_bill_start_gate.dart`.

A booking still waiting for the carrier holds the start too (owner, 23 Oct 2026): every not deleted `PENDING_CARRIER_ACCEPT` shipment whose payment would let it be accepted (authorized, or MOCK captured) is listed in the same `409 eway_bill_not_ready` with `reason: "waiting_for_accept"`, before every bill entry, since the carrier acts on it. The error keeps its name so app builds already installed still read the bill lines; an older build drops the reason it does not know. A waiting booking whose checkout is not done (payment `CREATED` or `FAILED`) does not hold the start: it cannot be accepted, and only the shipper can change that, so it would hold the trip with nothing the carrier can do. `GET /v1/pilot/carrier/shipments` gives each `PENDING_CARRIER_ACCEPT` shipment `readyToAccept: true | false` (carrier logins only, drivers included; no payment status or amount), which the app uses to mirror this. The check is in `startAnchorTripAsPilot` (`apps/api/src/services.ts`). No Remind for these: `eway-bill-reminder` still answers `409 eway_bill_not_holding_start` for a booking not accepted.

When the trip starts, each such booking is closed (owner, 23 Oct 2026; `closeBookingsLeftBehind` in `services.ts`): status `FAILED_CARRIER_REFUNDED`, the status Finance's cancel gives, with `leftBehindAtUtcMs` set (every role that reads the shipment gets it), its weight taken off the trip's `reservedKg`, an audit row `SHIPMENT_LEFT_BEHIND` by the person who started the trip (`PENDING_CARRIER_ACCEPT` → `FAILED_CARRIER_REFUNDED`), and integration event `load.cancelled`. No money moved, so nothing goes to Razorpay and the payment stays `CREATED` or `FAILED`. Each shipper login on it gets one notification, `eventKey: "shipment.left_behind"`, title "This trip left without your shipment", body "If your bank shows a payment, it comes back within 3 days. Book another trip when you are ready."; the carrier gets none, and no closed or cancelled shipment hears `trip.started` or `trip.completed`. A refused start closes nothing. If Razorpay had already reported a capture for it (payment `RAZORPAY` and `CAPTURED`, which authorize-only orders should not produce), the payment becomes `CAPTURED_AFTER_CANCEL` with an audit row `PAYMENT_AFTER_CANCEL` (`reasonCode` `CAPTURED`), so it is on Finance's `collectedAfterCancel` list, and the notice body reads "NaviG8r is refunding your payment. Your bank may take 5-7 working days." A payment that lands later goes through the webhook's cancelled-shipment path below: a capture goes on the same list, an authorization is only recorded and Razorpay releases it. Paying after the start is refused: `POST /v1/payments/razorpay/confirm` answers `409 { "error": "trip_already_started", "detail": "This trip has already left. You were not charged." }` for a closed booking, or one still `PENDING_CARRIER_ACCEPT` on an `IN_PROGRESS` or `COMPLETED` trip (checked after the order id and signature, and after an already authorized payment, which still answers `200`). A trip whose carrier asked to cancel it is not refused, since it may still go and the webhook would record the payment anyway. Booking a started trip was already refused (`400 anchor_trip_not_open`); if the trip starts while `/shipments/book` waits for the Razorpay order, the booking answers the same `409 trip_already_started` and stays closed, and an integration load reads `checkoutRequired: false` once closed.

A booking whose payment is still not done (`CREATED` or `FAILED`) 40 minutes after it was made closes: the shipper is told 30 minutes (`UNPAID_BOOKING_EXPIRY_MS` in `config.ts`), and the 10 minutes after (`UNPAID_BOOKING_GRACE_MS`) let a payment finished just in time land. The app opens Razorpay Checkout with `timeout` 1500 seconds (25 minutes); Razorpay's Standard Checkout docs say that after it "the customer will not be able to use Checkout", and warn that a browser that pauses timers in a background tab can keep it open longer. It closes the same way, whatever the trip's state (`expireUnpaidBookings` in `services.ts`, run before every request, so it needs no timer; a load made through the integration API is never closed this way, and the ERP lookups by `externalLoadId` and by `Idempotency-Key` skip a booking it closed): status `FAILED_CARRIER_REFUNDED` with `expiredUnpaidAtUtcMs` set, its weight taken off `reservedKg` (a `FULL` trip goes back to `OPEN`), an audit row `BOOKING_EXPIRED_UNPAID` by `system:unpaid-booking-expiry`, integration event `load.cancelled`, and the payment left as it is. Each shipper login gets one notification, `eventKey: "shipment.booking_expired"`, title "This booking expired", body "This booking expired because it was not paid within 30 minutes.", followed, when the payment is `RAZORPAY` with an order (so the shipper may have paid), by "If your bank shows a payment, it comes back within 3 days of when you paid. Your bank may take 5-7 more working days." (`BOOKING_EXPIRED_MONEY_SENTENCE`); the carrier gets none. A confirm that arrives after that answers `409 { "error": "booking_expired", "detail": "This booking expired because it was not paid within 30 minutes. If your bank shows a payment, it comes back within 3 days of when you paid. Your bank may take 5-7 more working days." }`, and a payment Razorpay still reports goes through the webhook's cancelled-shipment path below.

#### `POST /v1/pilot/anchor-trips/:tripId/shipments/:shipmentId/eway-bill-reminder`

For a `BOOKED`, not deleted shipment on an `OPEN` or `FULL` trip whose bill holds the start, each shipper login on it gets one notification: `eventKey: "eway_bill.blocking_start"`, title "The trip is waiting for your e-way bill", body by reason ("Add the e-way bill for this shipment, or say none is needed." · "Add the truck on the portal, then here." · "The truck on your e-way bill is not the truck on this trip. Check the truck on the portal, then here." · "The valid-until time you entered has passed. Check the bill on the portal, then enter the new time here." · "NaviG8r found a problem with your e-way bill. Check the details here and on the portal."), and `data.reason` set to the reason. Response `200 { "sent": true }`. While an unread one for that shipment with the same reason is there, or one for the same reason was sent in the last 6 hours, read or not (owner, 23 Oct 2026), nothing is sent and the answer is `200 { "sent": false, "why": "already_reminded" }`; with a different reason, the unread one is marked read and the new one sent. Refusals: `404` for a shipment not on this trip, `409 { "error": "trip_not_startable" }` for a trip not `OPEN` or `FULL`, `409 { "error": "eway_bill_not_holding_start" }` when the bill does not hold the start (or the booking is not accepted), `409 { "error": "trip_has_no_truck", "detail": "Choose a truck first." }` for `truck_differs` while the trip has no truck. #### `POST /v1/pilot/anchor-trips/:tripId/complete`
Carrier marks the load done (`IN_PROGRESS` → `COMPLETED`). #### `POST /v1/pilot/carrier/shipments/:shipmentId/accept`
Carrier accepts a customer booking (`PENDING_CARRIER_ACCEPT` → `BOOKED`). Payment must be authorized (or MOCK captured).

Once the trip has started, no booking can be accepted onto it (owner, 23 Oct 2026): on an `IN_PROGRESS` or `COMPLETED` trip the answer is `409 { "error": "trip_already_started", "detail": "This trip is already on the way, so it cannot take this booking." }` and nothing changes. Checked after `shipment_not_acceptable` and before every other check. The sentence goes to drivers too; the app shows it under a disabled Accept before it is tapped. Starting the trip closes every booking still waiting whose checkout is not done (see the start route), and one ready to accept holds the start, so only a booking stored before that rule can still be waiting on a started trip. Such a booking stays `PENDING_CARRIER_ACCEPT`, and while it does the trip cannot complete (`shipments_still_active` from the complete route); Finance can end it with `POST /shipments/:id/fail-refund`, which takes a `PENDING_CARRIER_ACCEPT` shipment on a trip in any status.

Optional body `{ "vehicleId": "..." }` (owner decision, 16 Oct 2026). When the trip names no truck and the caller holds `trip.assign` (owner, owner-driver, dispatcher), the trip's truck is set to that vehicle in the same request, after every other acceptance check and before anything is written; the driver stays as it was. Audit row `TRIP_ASSIGNED` on the trip, state words only, as for the assignment route. The vehicle must be an active truck of the trip's carrier, or `400 { "error": "invalid_trip_assignment", "detail": "Choose a truck from your own fleet.", "field": "vehicleId" }` and nothing is accepted or named. #### Carrier transporter ID

One optional field on the carrier organization, `transporterId` (owner decision, 16 Oct 2026): the 15 characters the e-way bill names its transporter by. **`PATCH /v1/pilot/carrier/transporter-id`** (permission **`transporter_id.write`**: carrier `OWNER` and `OWNER_DRIVER`, the people who set bank details; `403` for dispatchers, drivers and everyone else). ### E-way bill (link-out demo)

The shipper types in an e-way bill made on the government portal, or says none is needed. Ops looks it up by hand and records what it saw. naviG8r never makes, changes or verifies a bill. Design and copy: `docs/design-eway-bill/contract.md`. The record is `shipment.ewayBill`, cut by role: shipper and ops get everything except user ids, carrier logins (owner, dispatcher, driver) get only the kind, the bill number, the truck and valid-until, the "not needed" reason and the check, finance and admin get nothing. ERP integration responses never carry it. **Database mode:** the `ShipmentRow."ewayBill"` JSONB column must exist first (`ALTER TABLE "ShipmentRow" ADD COLUMN "ewayBill" JSONB;`), or every shipment read fails.

#### `POST /shipments/:id/eway-bill`

Shipper (`eway_bill.write`), own shipment, until delivery is accepted. Replaces the record and clears ops' check.

```json
{ "kind": "BILL", "billNumber": "1234 5678 9012", "billDate": "2026-10-01", "makerGstin": "29ABCDE1234F1Z5", "invoiceNumber": "INV/1" }
{ "kind": "NOT_NEEDED", "reason": "BELOW_THRESHOLD | GOODS_EXEMPT | OTHER", "note": "required with OTHER, 3 to 140 characters" }
```

Response `200 { "shipment": { ..., "ewayBill": {...} } }`. Refusals: `400 { "error": "invalid_eway_bill", "detail": "a sentence", "field": "billNumber" }`, `409 eway_bill_locked`.

#### `POST /shipments/:id/eway-bill/remove`

Shipper. Back to "nothing added". Removing twice is harmless. Same response and `409` as above. Once the trip has started (`IN_PROGRESS` or `COMPLETED`; owner, 23 Oct 2026) removal is refused, checked after `eway_bill_locked`: `409 { "error": "trip_started", "detail": "The trip has started, so the e-way bill cannot be removed." }`, and the bill stays. Editing it with the route above is still allowed. The app hides Remove e-way bill once the trip is on the way.

#### `POST /shipments/:id/eway-bill/truck`

Shipper (`eway_bill.add_truck`: customer admin and member), own shipment, until delivery is accepted, only on a `BILL` (`409 eway_bill_not_entered` otherwise). Body `{ "truckNumber": "KA01AB1234", "validUntilUtcMs": 1792000000000 }`, typed in after the shipper added the truck to the bill (Part B). Clears ops' check. Same response as above; refusals `400 { "error": "invalid_eway_truck", "detail": "a sentence", "field": "truckNumber" }`, `409 eway_bill_locked`. Audit row `EWAY_BILL_TRUCK_ADDED`, state words only.

**Carriers only read the bill (owner decision, 18 Oct 2026).** Every carrier login (owner, owner-driver, dispatcher, driver) gets `403 { "error": "forbidden" }` here, and the old carrier route `POST /v1/pilot/carrier/shipments/:id/eway-bill/truck` answers the same `403` to everyone who can see the shipment (others still get `404`), so an older carrier app is refused rather than told `404`.

#### `GET /ops/eway-bills`

Ops (`eway_bill.check`). `{ "toCheck": [shipment], "missing": [shipment], "notNeeded": [shipment] }`, oldest booking first. `missing` is shipments waiting for a carrier or booked with no record.

#### `POST /ops/eway-bills/:shipmentId/check`

Ops. `{ "result": "FOUND", "billNumber": "123456789012" }` or `{ "result": "PROBLEM", "problemReason": "NOT_FOUND | CANCELLED | DETAILS_DO_NOT_MATCH | OTHER", "billNumber": "..." }`. `billNumber` is the bill ops looked up; if the shipper has since replaced it the answer is `409 eway_bill_changed`. Only on a `BILL` (`409 eway_bill_not_entered` otherwise). Last writer wins. Audit rows `EWAY_BILL_ENTERED`, `EWAY_BILL_NOT_NEEDED_STATED`, `EWAY_BILL_REMOVED`, `EWAY_BILL_CHECKED` hold state words only.

### Existing marketplace endpoints (still available)
- `GET /anchor-trips` (list + `GET /anchor-trips/:id`) lists trips for the customer pilot; **enabled in production** as part of the public marketplace. The list leaves out `CANCEL_REQUESTED` and `CANCELLED` trips.
- `POST /shipments/quote` quotes a shipment. It needs `Authorization: Bearer` for a login with `load.create` (shippers and ops): without one it answers **401**, and a carrier login gets **403**. Body **`weightKg`** (required); optional **`pickup`** / **`drop`** (`GeoPoint` each — send **both** or **neither**); optional **`anchorTripId`**. Response includes **`grossPaise`** plus **`breakdown`** (`pricingMode`, `laneKm`, `shipmentKm`, `distanceKmForPrice`, `modelVersion`, component paise). Booking uses the same formula when coords allow distance pricing.
- `POST /shipments/book` books against an `anchorTripId`. With `Authorization: Bearer` from OTP for a user in a **CUSTOMER** org, the shipment is tagged with `customerOrgId` and `customerOrgName` from that org (otherwise anonymous booking uses only the body `customerOrgName`). Optional **`customerPhone`** or **`bookedByPhone`** (India mobile, same normalization as registration) stores `bookedByPhone` on the shipment so the same person can list it after OTP **without** relying on org name matching.
  - **`PAYMENT_PROVIDER=MOCK` (default):** response **`201`** `{ shipment, payment }` where `payment.status` is **`CAPTURED`** immediately.
  - **`PAYMENT_PROVIDER=RAZORPAY`:** after booking, server creates an order with **`payment_capture: false`**. Response **`201`** **`{ shipment, payment, razorpayKeyId? }`** — `payment.status` starts **`CREATED`** with **`razorpayOrderId`**. Flutter (or Web) opens Razorpay Standard Checkout with **`key`=`razorpayKeyId`**, **`order_id`=`razorpayOrderId`**, and amount from `payment.amountPaise`. After customer pays, **authorization** is applied when Razorpay calls **`POST /v1/payments/razorpay/webhook`** (`payment.authorized` / `payment.failed`). **Capture** happens on **`POST /shipments/:id/pod`** (server captures before ledger). Booking may be rolled back if order creation fails.
- `GET /shipments`, `GET /shipments/:id`, and **`GET /shipments/:id/tracking`** require `Authorization: Bearer`. Responses include shipments for your **CUSTOMER** org (`customerOrgId` match, or legacy match on `customerOrgName` vs org `displayName`) **or** shipments whose **`bookedByPhone`** equals your user’s phone.
- `POST /shipments/:id/pod` and `POST /shipments/:id/fail-refund` require the same Bearer and the same visibility rules as GET. With Razorpay, POD triggers **capture** then delivery/ledger logic. **`fail-refund`** (Finance, `payment.refund`) cancels a `PENDING_CARRIER_ACCEPT` or `BOOKED` shipment (`FAILED_CARRIER_REFUNDED`) and: for a **CAPTURED** payment, asks Razorpay to refund it (`REFUNDED`); for an **AUTHORIZED** one with a Razorpay payment or order id, sends nothing, because Razorpay refunds only captured payments and releases an authorization nobody captures within 3 days of payment by itself (`HOLD_RELEASED`, audit row `PAYMENT_HOLD_RELEASED` instead of `PAYMENT_REFUNDED`; owner decision, 19 Oct 2026); for an unpaid one (`CREATED` or `FAILED`), moves no money (`REFUNDED`). An **AUTHORIZED** payment with no Razorpay ids (an ERP `erp_preauthorized` booking) is no Razorpay hold and is refused as before, `400 razorpay_payment_id_missing`. The shipper gets a "Shipment cancelled" notification naming the trip's cities and saying which happened: "NaviG8r never collected this payment. Razorpay returns it within 3 days of when you paid; your bank may take 5-7 working days after that." for a held one, "Your refund has started." for a collected one, and "Nothing was charged." only for `CREATED` or `FAILED`.

#### `GET /health`
Returns **`{ ok: true, persistence: "file"|"db", paymentProvider: "mock"|"razorpay" }`** — useful when wiring Razorpay and Postgres locally.

#### `POST /v1/payments/razorpay/webhook`
**Unauthenticated** (signature only). Razorpay posts the JSON event body raw; validate **`x-razorpay-signature`** using **`RAZORPAY_WEBHOOK_SECRET`**. A body over 256 KB answers **`413 payload_too_large`** before the signature is checked. Implemented events: **`payment.authorized`**, **`payment.captured`**, **`payment.failed`**. The server finds the internal payment by Razorpay order/payment ids and updates state idempotently. An event for a payment whose shipment is cancelled (`FAILED_CARRIER_REFUNDED`) never brings the shipment back. A `payment.authorized` or `payment.captured` for it is recorded instead: one audit row `PAYMENT_AFTER_CANCEL` per Razorpay payment and event (resource the shipment, `previousState` and `newState` the payment status, `reasonCode` `AUTHORIZED` or `CAPTURED`, `razorpayPaymentId` the event's Razorpay payment id, actor `system:razorpay-webhook` with `source` `SYSTEM`; the amount is the payment's `amountPaise`, since an audit row has no amount field), visible to `FINANCE` in `GET /v1/audit`. So two Razorpay payments on one shipment are two rows, and an event Razorpay sends twice is one. A capture also sets the payment to `CAPTURED_AFTER_CANCEL` and saves the captured id in `capturedAfterCancelRazorpayPaymentId` (`razorpayPaymentId` is not overwritten), which `/ops/beta` shows for Finance to refund in the Razorpay dashboard and then mark refunded (`mark-refunded`, above); nothing is refunded automatically. A second, different capture while the first still waits keeps the first id on the payment and has its own audit row; once Finance marks the first refunded, the payment takes the second's id and stays on the list for Finance. Ignored as already known: an authorization for the Razorpay payment NaviG8r already held, and a capture for the Razorpay payment it already refunded. In database mode neither `capturedAfterCancelRazorpayPaymentId` nor the audit row's `razorpayPaymentId` is saved (no column for either), so after a restart the card loses the id and a resent event may be recorded again; no environment runs database mode today. A late `payment.failed` changes nothing. Configure this URL on the Razorpay dashboard (test mode webhook for dev).

**Production vs legacy demo:** legacy admin/demo JSON that exposes or mutates operator state (`/admin`, `/v1/users`, unauthenticated legacy `/carriers` list/create, legacy `POST /anchor-trips`, ledger/payout toys, **`POST /v1/pilot/driver/login`**, etc.) returns **403** unless `ENABLE_LEGACY_DEMO_SURFACE=1`. The customer marketplace routes above stay enabled in production; without a Bearer token, protected shipment routes return **401**.

## Location-based MVP extension (maps + lane eligibility)

This section upgrades the MVP to be **location-based** (lat/lng + maps), while keeping the existing city-string fields for backwards compatibility during rollout.

### Goals
- Driver publishes anchor trips with **origin + destination on a map** (Google Maps).
- Customer sees **eligible lanes** for their desired shipment (pickup/drop + weight).
- Bookings are treated as **en-route** (pickup/drop should lie along the trip lane, with reasonable detour tolerance).

### New types (MVP)

#### `GeoPoint`
```json
{
  "lat": 28.4595,
  "lng": 77.0266,
  "placeId": "ChIJ...optional",
  "label": "Gurugram (optional)"
}
```

Notes:
- `placeId`/`label` are optional but useful for UI and debugging.
- Canonical matching is based on **lat/lng**.

### AnchorTrip (location-based fields)
When enabled, an anchor trip includes:
- `origin`: `GeoPoint`
- `destination`: `GeoPoint`
- Optional: `routePolyline` (encoded polyline, computed client-side or server-side later)

Backwards compatibility:
- During rollout, keep `originCity` / `destCity` populated for UI fallbacks.

### Shipment booking (location-based fields)
When enabled, a booking includes:
- `pickup`: `GeoPoint`
- `drop`: `GeoPoint`
- Optional: `laneMatch` describing why it is eligible (explainable scoring)

### Driver: publish anchor trip (location-based)

### Customer: eligible trips for a shipment request

#### `GET /v1/customer/eligible-anchor-trips`

- Reserve capacity immediately (`reservedKg += weightKg`)
- If capacity becomes fully reserved, mark trip `FULL`

### Phase C: en-route status + detour tolerance (accepted)

#### En-route semantics
Bookings are considered **en-route** if pickup/drop are “along the lane” within acceptable detour limits.

#### Detour policy (MVP)
Define detour tolerance with simple thresholds:
- `maxPickupDetourKm` and `maxDropDetourKm` (e.g. 10–20 km)
- Optional `maxTotalDetourKm` for combined pickup + drop (e.g. 25–40 km)

Eligibility computes and returns `detourKmEstimate` so the UI can explain why a lane is eligible/ineligible.

Future upgrade (non-MVP):
- Use actual route distance deltas from Google Directions to compute detour cost.

### Ops: deactivate user (soft-delete / tombstone)

#### `DELETE /v1/ops/users/:userId`
#### `DELETE /v1/ops/users?phone=10digits`

Requires Ops Admin/Agent Bearer. **Soft-deletes** the user — rows are marked INACTIVE (`inactiveAtUtcMs` + `inactiveReason`) and **retained for audit**. Nothing is hard-erased from the store/DB.

**Cascade rules**
- Always: revoke auth sessions; expire pending OTPs; deactivate user, driver profile, and memberships.
- **Sole-owned orgs** (user is the last *active* member, not PLATFORM): deactivate org plus vehicles, trips, shipments, payments, ledger lines; revoke ERP connections/keys for that org.
- **Shared orgs**: deactivate this user's membership only. If sole `OWNER` / `OWNER_DRIVER` / `CUSTOMER_ADMIN` of a shared org → `409 sole_owner_of_shared_org` unless `force=1`.
- **Active work** (open shipments or `IN_PROGRESS` trips) → `409 active_work_exists` unless `force=1`.
- Cannot deactivate yourself (`403 cannot_delete_self`) or the last active ops admin.
- Inactive users cannot OTP login (`account_inactive`); existing tokens fail bearer checks.

Query: `force=1` to override active-work / sole-owner-of-shared-org guards.

Admin UI: `/admin` → Ops Admins card → **Deactivate user**.

After PR #136 lands, apply the same OTP behavior to `adminDashboardV1.ts`: retain the `challengeId` from `/v1/auth/otp/start`, use its optional generated `debugCode`, clear both values before resend and when start fails, and show retry guidance for expired, incorrect, or superseded challenges.

If using `PERSISTENCE=DB`, run `npx prisma db push` after deploy so `inactiveAtUtcMs` / `inactiveReason` columns exist.
