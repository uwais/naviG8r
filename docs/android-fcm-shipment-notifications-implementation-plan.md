**Status:** Implementation, requested code reviews, and development Firebase device testing are complete. Work remains local on the feature branch; no merge or production enablement has occurred.

**Design:** [Android FCM shipment notifications technical design](android-fcm-shipment-notifications-design.md), accepted by Luna-High and Astra-High on 2026-10-11.

## Delivery objective

Add Android FCM system notifications for the existing shipment notification/message events. Keep the current in-app inbox and timeline authoritative, use generic privacy-safe lock-screen content, and route taps through current authenticated authorization. Support development testing from a locally running API over LAN. Keep production delivery disabled by default; an explicitly approved single-process FILE pilot may opt in with `PUSH_ALLOW_FILE_PRODUCTION=1` while PostgreSQL migration remains deferred.

### 1. Common Store mutation/persistence coordinator

- [ ] Introduce one coordinator around Store mutations and persistence, accessible to HTTP request handlers, payout/webhook timers, and the FCM worker. Preserve existing per-request auth/request context and Store object/map references used by service code.
- [ ] Migrate payout timer mutations through the coordinator. Refactor webhook delivery processing into three short coordinated stages: claim/snapshot and persist lease; perform external HTTP send outside the coordinator; conditionally persist completion only if its lease/generation is current. Never hold the global coordinator during provider/webhook network I/O.
- [ ] Add deep snapshot/rollback support for every map, nested mutable record, counter, index, and source transition changed by coordinated operations: shipment/workflow state, payment/ledger/audit/event snapshots, notifications, webhook/payout state, device registrations, push intents, deliveries, and leases. Restore contents in place where service code retains Store/map references; shallow Map copies are insufficient for nested webhook mutation.
- [ ] Keep all push state in the same Store snapshot/persistence path in this first slice. Add push arrays additively to FILE v7 and the DB integration snapshot without changing the existing format/schema version; verify current v7 snapshots hydrate unchanged. An older binary may ignore/drop push-only state on rollback, so keep flags off and preserve all canonical Notification/Conversation/Shipment state; production delivery remains gated by the explicit persistence-mode policy.
- [ ] Keep FCM network I/O outside the coordinator: atomically claim and persist a lease, send, then reacquire the coordinator and update only if lease owner and device generation still match.
- [ ] Preserve single-writer deployment assumptions. Do not claim multi-instance worker safety.

**Tests:** failed persist followed by later unrelated save does not leak any in-memory mutation; overlapping HTTP/timer/worker save tests; slow webhook does not block ordinary HTTP mutations or FCM work; stale webhook completion cannot overwrite newer state; claim/complete lease ownership race; expired lease recovery; crash/retry after provider accepted but before outcome persisted; credential-free load test measures API latency and queue progress during full-Store saves.

**Gate:** Persistence and rollback tests pass before device registration or sending logic is added.

### 2. Push state, event fanout, and authenticated API

- [ ] Add Store types/maps and migration/serialization for `PushDevice`, `PushIntent`, and per-installation `PushDelivery` with ownership generation, independent attempts, retry time, lease, expiry, and provider outcome. Keep canonical in-app notifications, messages, reads, and shipment history out of push cleanup/expiry.
- [ ] Add an explicit bearer-only route path for user-scoped endpoints before normal selected-organization resolution; normal `rbacRoutes.ts` dispatch currently expects an organization. Test missing selection and stale/unauthorized `x-organization-id` headers.
- [ ] Device registration/revocation endpoints derive `userId` from bearer auth, enforce Android platform and token/installation validation, bounded active installations (initial limit: 5), explicit consent, current permission/channel hints, token uniqueness, and token rotation. Set initial limits: at most 10 register/revoke requests per authenticated user per minute and 60 open-resolver requests per user per minute; additionally cap by source IP at 30 registration and 120 resolver requests per minute. Reject bodies over 8 KiB and IDs over 128 characters; return a generic `429` with bounded `Retry-After`. Never return tokens. Reassess limits from observed non-PII metrics before production.
- [ ] Route all logout paths through best-effort authenticated revocation before `api.clearToken()` clears credentials; audit every existing direct token-clear call. Persist an account-scoped local revocation marker containing original account/install/generation, never replay it with another account's bearer token. On same-account reconnect, revoke only that generation; on account reassignment, server increments generation and old revocation becomes a no-op. Order registration/revocation to prevent a stale marker from revoking a newer registration. Clear pending notification routes and visible app notifications on account switch/logout.
- [ ] Add authenticated notification-open resolver that accepts only an opaque notification ID. Resolve the original recipient/organization/shipment from canonical state independent of selected organization, then verify current user, membership, and shipment/conversation access. Unauthorized IDs return a safe not-found result.
- [ ] Extend the existing event/message notification creation path to enqueue one `PushIntent` atomically with each canonical recipient Notification, and snapshot currently opted-in devices into independent deliveries. New devices receive no historical push backfill.
- [ ] Fanout only to current eligible SHIPPER/CARRIER recipients already used by the in-app notification catalog. Preserve recipient-specific authorization checks; no default OPS/FINANCE/ADMIN push.
- [ ] Generate an opaque, stable presentation key per recipient/shipment. Push payload contains only schema version, notification ID, presentation key, and generic copy; it contains no shipment ID, org ID, message body, or sensitive event attributes.

**Tests:** spoofed identity, token reassignment/rotation, stale token invalidation cannot revoke a newer generation, no device backfill, intent creation rollback, duplicate idempotency, recipient access revocation, resolver with missing organization selection and stale/unauthorized `x-organization-id`, registration/open rate limits, payload-size bounds, privacy/log redaction.

**Retention tests:** cleanup is coordinator-owned, bounded, and restart-safe in both FILE and DB persistence. Old-schema/old-FILE migration preserves existing notification sequence, notifications, messages, and shipment history. Expired push state remains deleted after reload; canonical in-app data is unchanged.

### 3. Sender and bounded retry worker

- [ ] Add an FCM sender adapter with an injectable fake implementation for tests and server-only service-account credentials loaded from environment/secret configuration. Prefer FCM HTTP v1 with a bounded/cancellable request: the inspected Firebase Admin Node SDK v14.5.0 hardcodes a 15-second messaging timeout and retries some failures internally, which conflicts with the planned 10-second application timeout and explicit attempt accounting. If the SDK is reconsidered, first prove its actual retry/timeout behavior and adjust lease/retry accounting. Establish whether DB-at-rest encryption covers registration tokens; if not, add envelope encryption before production. Never use production tokens in local test data; an approved production FILE pilot must use a durable disk and stable encryption key.
- [ ] Add flags defaulting off for device registration, event enqueue, and sender execution before any enqueue path is enabled. No credentials or project config are committed. Reject startup/configuration when production sender is enabled with FILE persistence unless the explicit single-process pilot opt-in `PUSH_ALLOW_FILE_PRODUCTION=1` is set.
- [ ] Use this initial transport policy: Android high priority for user-visible shipment alerts; FCM notification-message delivery; total intent lifetime 24 hours from source event; submission retry horizon 6 hours; maximum 8 application `send()` invocations per delivery including the first call; 10-second transport request timeout when the selected sender actually cancels the underlying request; maximum four concurrent sends per single worker process.
- [ ] For transient errors, wait at least 10 seconds before retry (at least 60 seconds for quota errors); use exponential backoff multiplier 2, ±20% jitter without crossing the minimum interval, and a 1-hour interval ceiling. Honor provider `Retry-After` without retrying earlier; if the requested delay exceeds the 6-hour retry horizon or source-event expiry, mark the delivery expired/suppressed. Compute each FCM transport TTL as `min(24h, intent.expiresAt - now)` and suppress sends when no positive TTL remains. Do not extend freshness on retries.
- [ ] Define timeout semantics with the selected sender: an application timeout is not proof the FCM request was cancelled. Do not release a delivery lease or start a duplicate send while the original send may still be active. Verify Firebase Admin SDK internal retry/cancellation behavior; use it only if the network request can be bounded/cancelled and retries are understood. Otherwise use the FCM HTTP v1 API with Google-auth token acquisition and an abortable request. Count one actual request submission as one attempt and ensure lease/deadline handling accounts for transport behavior.
- [ ] Use a lease duration longer than the bounded send deadline (initially 30 seconds for a 10-second cancellable request), and recover only after expiry with a generation/lease-owner conditional check.
- [ ] Treat the guarantee as bounded at-least-once submission attempts and best-effort device delivery; notification messages can be delayed, duplicated, missing, or coalesced. Do not configure a shared collapse key that implies per-shipment delivery.
- [ ] Recheck current recipient access, device owner, token, consent state, and ownership generation immediately before send. The server cannot verify current Android permission/channel state.
- [ ] Revoke invalid/unregistered tokens only when token and ownership generation still match. Persist bounded provider error codes; never log payload text, raw tokens, or credentials.
- [ ] Add queue metrics/log fields without PII: queue age, attempt count, accepted/permanent/transient outcomes, invalid token count, provider latency, and suppressed delivery count. Include safe expiry/disable behavior; no manual redrive endpoint in the first version unless ops review approves it.
- [ ] Retention proposal: delete FCM token immediately on device revocation; retain revoked device tombstones and terminal `PushIntent`/`PushDelivery` metadata for 30 days, then purge them through bounded cleanup. Preserve canonical Notification/Conversation/Shipment data under existing retention policy. Keep stable presentation-key derivation independent of pruned delivery rows. Document and test push metadata retention separately from in-app history retention.

**Tests:** fake sender accepted/transient/permanent/invalid-token/time-out responses, bounded attempts and expiry, provider `Retry-After` minimum respected (never retry early) and delivery expiry when the requested delay exceeds its horizon, concurrency limit, crash window duplicate send, authorization and ownership recheck, feature flags.

### 4. Flutter Android registration, notifications, and routes

- [ ] Add Android-only Firebase configuration initialization, FCM token lifecycle, app-installation identity, notification permission/consent state, and stable user-visible channel creation.
- [ ] Request Android 13+ permission only after explaining value; register only after permission and explicit opt-in. In-app inbox keeps working when denied. Refresh permission/channel status when app resumes; OS state remains authoritative.
- [ ] Register/update the device on sign-in/token rotation and revoke on account switch/logout. Avoid server registration while signed out. Do not persist FCM credentials in insecure storage.
- [ ] Foreground `onMessage` displays a generic local Android notification using presentation key as tag and ID `0`; FCM background display uses the same tag, ID `0`, and channel. No custom group-summary notification.
- [ ] Implement FCM `onMessageOpenedApp`/`getInitialMessage` and local-notification response/terminated-launch callbacks distinctly. Validate payload schema and hold an opaque pending notification ID through initial sign-in only, bounded by expiry. Cancel on explicit logout/account switch/denial/stale auth generation.
- [ ] Call the authenticated open resolver, then navigate using the returned authorized org/shipment route; refresh inbox and timeline. Do not navigate based solely on payload or mark read on tap.
- [ ] Guard platform-specific Firebase setup so Flutter Web and existing non-Android test targets remain operational.

**Tests:** Dart unit/widget tests for permission states, opt-in, token rotation, callback distinction, bounded pending route, auth-generation fencing, denied access, and resolver-driven navigation. Android device/emulator test for replacement identity and tray cleanup.
